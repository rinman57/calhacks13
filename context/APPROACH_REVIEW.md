# Approach review — October 24, 2026

## Recommendation

Keep incremental extraction and parallel verification. Simplify coordination to
one fixed pool of three claim workers. Each worker researches one claim, saves
its evidence, and makes a fresh assessment call with no tools. Separate model
conversations preserve the research/assessment boundary without requiring
separate worker pools or assessor counts based on video claim count.

The product should prioritize a small number of useful, traceable checks during
viewing. Throughput alone is not success: researching irrelevant claims faster
increases cost and makes the sidebar harder to trust.

This is a proposed direction, not a runtime change. The user's stress-test
symptoms and desired coverage still need to inform the implementation.

## Problems to address in order

1. **Citation repair can conceal a grounding failure.**
   `extract/verify.py::_align_verdict` substitutes the first saved fetched passage
   when an assessor supplies an unknown passage ID. It can also attach the whole
   explanation to a passage automatically. That makes the reference structurally
   valid without establishing that the passage supports the explanation. Existing
   tests explicitly accept this behavior. Keep the existing bounded correction
   attempt, then report an assessment failure if references remain invalid.
   A factual verdict of insufficient evidence should be written by the assessor
   when warranted, not used to disguise invalid output or execution failure.

2. **The workload needs a product boundary.**
   Exact quotation is necessary but does not establish that a sentence deserves
   web research. Preserve genre/title context and require a complete, externally
   checkable assertion. Start with a configurable review budget, provisionally
   five high-value claims per run, while retaining other discovered candidates
   with an explicit deferred state. Validate this choice with the user: exhaustive
   coverage requires a different latency/cost tradeoff. Avoid another agent call
   just to perform this gate.

3. **Concurrency is bounded per job, but backlog and total work are not.**
   The current session uses three research workers plus up to four assessor
   threads; both pending research submissions and the assessor queue are
   unbounded. Every POST starts another session. Navigating away stops displaying
   that job but does not cancel its work. Use a fixed claim pool, a small bounded
   backlog, a shared server concurrency limit, duplicate active-job reuse, and a
   cancellation signal checked before each new external call. Do not increase
   worker count with claim count.

4. **Late claims inherit an older deadline.**
   The 480-second deadline starts in `VerificationSession.prepare`, before claim
   extraction, and is shared by all claims. Give each worker a per-claim deadline
   when it starts, retain a separate explicit overall job budget, and pass the
   remaining time to external requests. Current checks between calls do not stop
   an already-running request. Continuation tool definitions also reuse their
   original limits; track observed uses and enforce the remaining per-claim
   budget rather than assuming a per-request limit is cumulative.

5. **The sidebar can look less reliable than the underlying run.**
   `extract/server.py::_verdict_cards` deliberately removes supported claims.
   `extension/content.js::renderVerdicts` recreates every card on each poll. The
   selected claim ID survives, but focus and the expanded More section do not.
   Keep keyed cards and show supported results, or offer an explicit filter with
   visible checked totals. Show actual queued/researching/assessing counts rather
   than a single sequential stage label. A finished extraction can currently be
   called done even when verification has failed because `ExtractionResult.ok`
   only requires a transcript or media artifact.

6. **Persistence is incomplete at the research/assessment boundary.**
   Evidence is only persisted in `_store` after assessment or a terminal failure;
   successful research waiting in the assessor queue is not yet saved. Save it
   before assessment. `claims.json` writes are not atomic, while server snapshots
   read that file during extraction. Make those writes atomic and publish a
   coherent job snapshot. Chunk resume/hashes from the handoff are also not
   implemented; defer a comprehensive resume system until the core flow is stable.

## Minimal target flow

```text
Timestamped transcript
  -> one chronological chunk extractor
  -> validate quote and eligibility; save candidates atomically
  -> admit claims within the run budget to a bounded queue
  -> three claim workers, each doing:
       research -> persist evidence -> fresh assessment -> validate -> persist
  -> poll one job snapshot; update stable cards by claim ID
```

Keep the existing providers, artifact formats, web provenance checks, transcript
timestamps, separate research/assessment prompts, and polling transport. No new
agent framework, manager model, or frontend framework is needed.

## Suggested implementation sequence and acceptance checks

1. Restore strict citation rejection and replace the tests that reward guessed
   passage substitution. Add a case with a real fetched but irrelevant passage:
   a wrong ID must not silently become a valid citation.
2. Collapse scheduling to the fixed pool; add claim/job budgets and persist
   evidence before assessment. Verify that a slow first claim does not block a
   later completed card and that a later-started claim gets its own time budget.
3. Make claim writes atomic, expose partial/failure/deferred states, retain keyed
   cards, and prevent duplicate active jobs from multiplying paid work.
4. Replay saved transcripts across a political factual clip, satire, a stunt,
   a health explainer, and a longer video. First label a small expected claim set
   by hand. Compare extraction precision, important missed claims, useful cited
   verdicts, invalid references, time to first claim/verdict, total time, actual
   tool/token usage, and errors. Record revision and configuration on each run.

Do not treat a decrease in insufficient-evidence verdicts alone as improvement.
The measurable objective is more useful, correctly cited results within an
agreed wait and research budget.

  expected behavior.
- Is the demo intended to flag a few important claims or check every factual
  statement? What wait is acceptable before the first useful result appears?
